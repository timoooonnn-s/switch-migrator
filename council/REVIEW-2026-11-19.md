## 1. Verdict against the brief

| # | The brief asks for | State | One-line verdict |
|---|---|---|---|
| 1 | Take output from the old switch | **Strong** | The best part of the tool. Connection layer, fallback chains, offline replay, snapshots, dry-run. |
| 2 | Config for the new switch, in company standard, on top of ZTP | **Missing** | It *copies* (VOSS) or *translates* (ERS) the **old** config, with **old** port numbers. It knows neither the company standard nor the ZTP baseline. |
| 3 | Aggregated config snippets for the new switch | **Partial** | Only MLT blocks are per new switch, and they have defects. Services come out per *old* switch, in a different file, in old numbering. |
| 4 | Cabling sheet: now / neighbours / where it moves | **Partial** | A good sheet of *where it is now*. *Where it moves* is a blank column for a human. |
| 4b | Hosts the switch cannot see | **Missing** | Nothing. Not even the configured port name is on the sheet. |

**The one structural reason behind 2, 3 and 4:** there is no *migration plan*
in the tool. The mapping *old port → new switch/port* — the thing every
deliverable depends on — only exists as cells a technician fills in by hand,
**during the window**, which the tool then reads back from Excel. So the
new-switch config can only be produced *after* the cables have moved. That is
the wrong way round: config should be reviewed days before, and the cabling
sheet should be a print-out of a plan, not the plan itself.

The tool grew out of a pre-migration **audit** (VLAN vs DvR fabric). That
audit is still its centre of gravity, and it is not one of the four things in
the brief.

## 2. The seats

### Field Engineer

> "I'd trust the data it collects with my life. I would not paste a single line
> it generates without rewriting it, and I still have to do the actual
> planning by hand in Excel."

What works for me:
* Read-only, `--dry-run` for the change board, offline replay, snapshots. I
  can collect on Monday and re-render all week without touching a switch.
* Usage classification with the *evidence* next to it. Down-but-in-a-live-MLT
  shown as a fault on a live cable is exactly right.
* Verification by MAC, and "no MAC yet" being a WARN, not a FAIL.
* Health check as a go/no-go gate with exit code.

What hurts:
1. **I do the mapping by hand.** 48 × N ports, NEW switch / NEW port typed
   into Excel. The tool knows the old port, the MLT, the SMLT pair, the
   neighbour — it could *propose* the mapping and let me correct it.
2. **The config arrives too late and in the wrong numbering.**
   `config/<old-switch>.cfg` has the old port numbers. `--generate-mlt` needs
   the filled-in sheet. Nothing gives me "here is everything to paste on
   `new-leaf-01`", reviewed before the window.
3. **The generated MLT config is wrong for our servers.**
   * Every dual-homed server in prod is a *single-member SMLT* per peer
     (`f110`, `f143` … on `gx-11-s72-p1`). `mlt_generate.plan()` flags every
     one of those as "an aggregation of one is a normal port with extra steps"
     (`mlt_generate.py:159`). On a real sheet that is dozens of false alarms,
     and the real ones drown.
   * LACP is switched on for **every** MLT (`mlt_generate.py:148`: any row with
     an old MLT id ⇒ `lacp=True`). The docstring says "carries the old MLT's
     LACP state forward"; it can't — the cabling sheet has no LACP column. A
     static MLT on the old side becomes an LACP MLT on the new side.
   * The old MLT *name* is carried over (`_pick_name`). Our names encode the
     port (`f110` = 1/10). After a move to 1/22 the name lies.
4. **The name of the thing on the port is not on the sheet.** VOSS `name` is
   parsed (`voss_config.py:166`, `port_names`) and then never used. ERS
   `name port` is parsed but only used by the ERS→VOSS generator. For a port
   with no LLDP, that name is often the only identity there is.
5. **Six separate runs** (audit, extract, sheets, health, generate-mlt,
   verify), 30 flags, a 16-item menu. I want three verbs:
   *collect · plan · verify*, and everything else is rendering.
6. **I ran an old version and didn't know.** This checkout is 11 commits
   behind. The tool prints its version, but nothing says "you are behind".

### Software Engineer

> "Individually the modules are well written and well tested. Together they
> have no spine: two front ends, no pipeline, one mutable god-object, and the
> company design hard-coded in string literals."

1. **No workflow layer.** `cli.main()` is ~290 lines of orchestration
   (`cli.py:557`). `menu.py` (1,115 lines) re-implements the same
   orchestration, imports `run_collection` / `collect_fabric` from `cli`, and
   fakes an `argparse.Namespace` (`menu.py:88`, `to_args`) to call them. Two
   front ends driving private helpers of each other. Wanted: one `workflow`
   package (collect / plan / render / verify) that both front ends call.
2. **`PortState` is a god-object filled by side effects.** Observed device
   facts, derived classification (`usage`), presentation (`uid`), and plan
   data all live on one mutable dataclass. `collect_switch()` calls
   `classify_audit()` (`collectors/switch.py:76`); the *report* layer assigns
   `uid` (`report/migration.py:35`). Separate:
   *facts* (immutable, from captures) → *derived* (pure functions) →
   *plan* (old→new) → *render*.
3. **Names that lie.** `PortState.description` holds the **media type**
   (`10GbSR`) — the one word a field engineer uses for the configured port
   name. `media` is a property returning `description`. Rename the field to
   `media` and add a real `name`.
4. **Snapshots store parsed objects, not evidence.** A parser fix cannot be
   re-applied to an old snapshot; `--save-raw` is a second, separate
   persistence format. Store raw captures (+ metadata) as the snapshot, and
   parse on load — one format, replayable with fixed parsers.
5. **Company design is hard-coded.** `config_generate.py:187-193` (flex-UNI
   boilerplate: `default-vlan-id 0`, `slpp-guard enable timeout 0`,
   `spanning-tree mstp edge-port true`), `config_generate.py:144` (port > 48
   ⇒ "SFP cage"), the `_HEADER` texts, the `smlt=True / flex_uni=True`
   defaults of `mlt_generate.plan()`. `port-preparer` already has the
   mechanism this needs (`profiles/default.yaml`, inheritance global → site
   category → role → scenario).
6. **The same knowledge lives in three repos.** VOSS parsers exist in
   `switch-migrator`, `port-preparer` and `networking-toolkit`; the I-SID /
   MLT / VLAN-name conventions live only in `port-preparer`. They will drift.
   Decision needed (see questions): one shared library, or switch-migrator
   imports `port-preparer`'s conventions.
7. **Docstrings are history books.** Many explain the defect that *used to*
   exist ("That difference used to be invisible…"). The *why* belongs in the
   docstring; the *story* belongs in git. README 963 lines + CONNECTIONS 828.
8. **Platform target unclear.** `requires-python >= 3.10`; RHEL 9's `python3`
   is 3.9 (your own TRuffle rule R2). Five runtime deps incl. a pinned
   `paramiko<4` — on a locked-down host each one is a ticket (TRuffle R1).

What I would keep untouched: `connection.py` and its runners, the parsers and
their fixtures, `usage.py`, `verify.py`, `health.py`, `cabling_sheet.py`'s
forgiving read-back. Good code, good tests.

### Fabric Architect

> "The tool has no idea what a finished new switch looks like. It cannot
> produce company-standard config, because the company standard is not in it."

1. **No ZTP baseline.** The VOSS extract keeps `VLAN CONFIGURATION` verbatim,
   so it emits `vlan create 4051 … type spbm-bvlan` / `4052` (B-VLANs — ZTP
   already made them) and `vlan members remove 1 1/1-1/48,2/1-2/6` (old
   hardware's port ranges). Pasted on a ZTP'd box that is errors at best. The
   tool must know what ZTP configured and emit only the **delta**.
2. **Wrong numbering everywhere.** VOSS→VOSS: old numbers verbatim. ERS→VOSS:
   ERS unit `2` port `7` becomes `2/7` (`config_generate._split`) — slot 2
   does not exist on a standalone VOSS leaf. A 4-unit ERS stack goes onto a
   *pair* of leaves; that mapping is a planning decision, not arithmetic.
3. **UNI model is assumed.** The ERS generator assumes flex-UNI. The one
   production VOSS leaf we have (`gx-11-s72-p1`) is **CVLAN / platform VLAN**,
   `FLEX-UNI disable` on every MLT. `port-preparer` says non-DC access is
   "VLANs only, no I-SIDs". Which model is the target, per site category?
4. **The company standard exists — elsewhere.** `port-preparer` knows:
   I-SID = `<250|251|270|271|299><VLAN 4 digits>` (250 ≡ 251, generate the
   lower), MLT id `4xx` for new LAGs, LACP key = MLT id, VLAN 1 and 31
   reserved, `1531100` = infrastructure I-SID, vIST/B-VLAN/NNI untouchable,
   `auto-sense` ports belong to ZTP. `switch-migrator` uses none of it (its
   example config still has offsets `10000/20000`).
5. **LACP syntax unverified.** The generator emits `mlt N member …` plus
   `interface mlt N / lacp enable key N`, and nothing on the member ports. The
   fixture's LACP MLT 197 has **no** `mlt 197 member` line, which suggests
   LACP membership on VOSS is driven from the port side. Needs one real
   running-config excerpt before the tool emits a single LACP line.
6. **DVR leaf mode is set** on the captured box. If the new leaves are DVR
   leaves, some config is forbidden there. Unknown.

### Rack Technician

> "Give me a sheet I can read with a torch, in the order of the faceplate,
> that tells me what's on the cable. Not 27 columns of VLAN maths."

1. **Too wide to print.** 27 columns "fit to width" on A4 landscape is ~5 pt.
   I need: Port ID · old switch/port · what is on it · new switch/port · ✔.
   The VLAN/I-SID detail is the engineer's, not mine. Two documents: a
   *rack sheet* and an *engineer sheet*.
2. **Wrong order.** Rows are sorted by usage, then by the port as a
   **string** (`report/migration.py:233`): `1/1, 1/10, 1/11, 1/2…` on VOSS and
   `1, 10, 11, 2…` on ERS. I walk the faceplate; the sheet should too.
3. **Empty rack columns.** "Rack (old)" / "Rack (new)" are blank because "no
   switch knows which rack it is in". The cabling documentation does.
4. **"UNCERTAIN, link down, age unknown" with no name** tells me nothing at
   the rack. Those are exactly the ports where I need the doc's host name.
5. **No patch panel.** Do we move the cable at the switch or at the panel? If
   at the panel, the sheet needs panel + panel port.

### Documentation Steward

> "The switch and the documentation each know half. The tool only reads one
> half, and nobody writes the documentation back afterwards."

* "Hosts you don't see" are, in practice: powered-off / cold-standby hosts,
  devices without LLDP that are silent (no MAC learned), passive things
  (patched through, media converters), and ports that are admin-down but
  cabled. The switch can, at best, say "link down since …". Only the
  documentation can say *what* is there.
* The documentation has **no API**. Options, best first:
  1. **Import a file the web tool already produces** — CSV/Excel export, or
     the page saved as HTML (Ctrl+S / print view), or a copied table pasted
     into a text file. No credentials, no scraping, works offline,
     reviewable. One small importer per format.
  2. **Physical walk-down** as the fallback: every cabled-but-silent port is
     on the rack sheet as "identify at rack", with a column to write the cable
     label.
  3. Browser automation against the web tool — **not recommended**: brittle,
     needs credentials, breaks on the next UI change, and needs IT's blessing.
* **Reconcile, don't merge.** Per (switch, port): *agree* · *doc-only*
  (invisible host — must be on the sheet, flagged "verify physically") ·
  *switch-only* (undocumented device — the doc is wrong) · *conflict* (doc
  says host A, LLDP says host B).
* **Write-back list.** Because the doc has no API, the tool should end the
  migration with a "documentation changes" sheet: every record that has to be
  edited by hand, old → new.

### Critic

1. **The audit is not in the brief.** The VLAN-vs-fabric comparison is the
   original purpose and still the most polished part. If it is a precondition
   someone else already guarantees, it should shrink to a check; if it is
   needed, it should be named in the brief.
2. **Scope creep while the brief is unmet.** Console-server access, profiles,
   handover bundle, run manifest, location split, coverage sheet, progress UI
   — ~9,500 lines, while goal 2 and goal 4b do not exist. Freeze these; do not
   extend them.
3. **Defects found by review, not by use.** The last eleven PRs are mostly
   "Fix N defects found reviewing…". That is good hygiene, but it also says the
   tool's feedback loop is review sessions, not migrations. How many real
   migrations has it carried?
4. **Fixtures are partly synthetic.** One production VOSS capture
   (`gx-11-s72-p1`), no production ERS capture, two "doc-derived" fixture
   sets. The ERS→VOSS generator has never seen a real ERS estate.
5. **"Never guessed" is not quite true.** The I-SID worksheet's paste-ready
   snippet pre-fills the lowest candidate (`isid.py:89`). Pasting it unedited
   is a guess — although it happens to match the "generate the lower" rule.
   Make it the documented rule, or leave the value empty.
6. **Two copies of the truth on migration night.** A stale checkout ran without
   warning. A migration tool should refuse, or at least shout, when it is not
   the version the plan was made with.

## 3. Chair's synthesis — proposed direction (not yet decided)

### The spine: a migration plan

```
collect ─▶ facts ─▶ PLAN (old port → new port) ─▶ render ─▶ verify
  raw       pure      proposed by rules,             config per NEW switch (standard − ZTP)
captures   parsing    edited by a human,             MLT/SMLT blocks
           + cabling  validated                      rack sheet · engineer sheet
           doc import                                verify commands · doc-change list
```

* **collect** — unchanged in spirit. Snapshot = raw captures + metadata.
* **facts** — pure parsing into immutable records, with provenance, merged
  with the cabling-doc import and reconciled (agree / doc-only / switch-only
  / conflict).
* **plan** — a `MigrationPlan`: per old port, a proposed new switch/port with
  the rule that proposed it, editable as YAML or as the Excel sheet, and
  validated (no double-booked port, SMLT legs on both peers, uplinks/vIST/NNI
  never moved, auto-sense ports untouched).
* **render** — everything is a rendering of facts + plan + standard:
  per-new-switch config (company standard, minus the ZTP baseline), MLT
  blocks, rack sheet, engineer sheet, verify commands, doc-change list.
* **verify** — against the plan, as today.

### Proposed package layout

```
switch_migrator/
  cli.py, menu.py         thin front ends; both call workflow/*
  workflow/               collect.py  plan.py  render.py  verify.py
  devices/                connection.py  commands.py  captures.py (raw store / snapshot)
  parse/                  voss/  ers/  common.py          (text → facts, pure)
  model/                  facts.py  plan.py  standard.py
  sources/                switches.py  cabling_doc.py  fabric.py
  standard/               profiles.py  conventions.py  templates/
  render/                 config/  sheets/  commands.py
  checks/                 fabric_audit.py  health.py  usage.py
```

### What to keep, freeze, fix

* **Keep as is:** connection layer, parsers + fixtures, usage, verify,
  health, sheet read-back, offline/dry-run.
* **Freeze (no new work until the brief is met):** console server, profiles,
  handover, manifest, location split, coverage, progress UI.
* **Fix now, independent of the redesign:** LACP-for-every-MLT, the
  single-member-SMLT false alarm, port-string sort order, port name on the
  sheet, `description`→`media` rename.

Nothing above is decided. It waits on the answers in `OPEN-QUESTIONS.md`.
